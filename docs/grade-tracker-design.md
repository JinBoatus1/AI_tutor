## Problem Statement
Students constantly want to know "where do I stand, and what do I need on the
remaining work to hit my target grade?" Today they answer this by hand off the
syllabus (often together with friends). AI Tutor already holds the student's
syllabus, study sessions, and weak topics — so it is positioned to answer this
*in context* while the student is learning, which a standalone calculator cannot.

## Demand Evidence
- The user's own lived behavior: in college they computed the needed final score
  by hand off the syllabus, **repeatedly, and with friends together**. A recurring
  social ritual around real grade anxiety — that is behavior, not interest.
- The status quo for many students is manual math, not even a tool.

## Status Quo (the real competitor)
- **RogerHub final grade calculator** (dominant, free, no login) and spreadsheets
  solve the *math* in ~10 seconds. The math is commoditized.
- Manual calculation off the syllabus.
- Key implication: this feature **cannot win on computing the needed score**. It
  wins on the number living where you study, grounded in your real course, and
  answered conversationally by the agent that also knows your weak topics.

## Target User & Wedge
- **User:** a student in a course with a weighted-category rubric and a target
  grade, who already studies in AI Tutor (has uploaded the syllabus).
- **Wedge (the only RogerHub-proof part):** grades → weak topics → study loop.
  Mid-chat: "what do I need on the final for an A?" → agent answers the number
  *and* "your weakest 3 topics are X/Y/Z, want to drill them?" Zero re-entry; one
  place for the whole course.

## Premises (confirmed with the user)
1. Lead with the **agent/study loop**, not a calculator. The needed-score number
   is a byproduct of the agent having your rubric + grades. AGREED (refined: the
   goal-seek is asked and answered inside the learning chat).
2. **Stage 1 = student self-enters grades.** Teacher-push deferred. AGREED.
3. **Rubric is parsed from the uploaded syllabus, but the student confirms/edits
   it.** Blind extraction will produce wrong grades and destroy trust;
   human-in-the-loop is non-negotiable. AGREED.
4. **Connects to existing Learning Progress** (weak topics), not a bolt-on
   calculator. AGREED.
5. **Teacher-pushed grades is a different, harder product** (gradebook/LMS;
   Canvas/Blackboard territory, FERPA, institutional sales). Kept as a vision
   slide. User agreed: "they are platforms, we are learning assistants."

## Chosen Approach: B — Dedicated Grades tab + agent integration

A new top-level surface for everything grade-related, with the rubric + grades
exposed to the Learning Mode agent so the goal-seek is also answerable in chat.

### Data model
- `Course` (per student, per term): `{ id, name, term, syllabusRef?, rubric }`
- `Rubric`:
  - `categories: [{ name, weight, dropLowest?: number }]` (weights sum to 100%)
  - `gradeCutoffs: [{ letter, min }]` (e.g. A>=93, A->=90, B+>=87, ...)
- `GradeItem`: `{ id, courseId, category, name, score, maxScore }` (student-entered)
- Computed `standing`: per-category average → weighted current grade (% + letter).
- **Goal-seek:** given a target letter (→ min %), solve for the needed score on a
  named future item (e.g. the Final), holding the rest as-is. Single-unknown solve.

### Syllabus → rubric extraction (reuse Auto Grader pipeline)
- Student uploads syllabus PDF. Reuse the existing FastAPI + OpenAI PDF pipeline
  that Auto Grader already uses.
- LLM proposes a structured rubric + a short "what matters in this course" summary.
- Student reviews/edits in the rubric editor (premise 3). Validate weights sum to 100%.

### UI (the dedicated tab)
- New route `/grades` (working name "My Course"), as a sidebar nav item (fits the
  in-flight sidebar work).
- Sections: (1) Course header + syllabus upload + AI summary; (2) Rubric editor
  (categories/weights + letter cutoffs); (3) Gradebook table (items grouped by
  category, add/edit scores); (4) Standing card: current grade (letter + %) and a
  visual what-if/goal-seek widget ("To get an A you need 87% on the Final").

### Agent integration (the wedge — ship in v1, not deferred)
- Inject the rubric + grades + computed standing into the Learning Mode agent as
  context, and/or expose a tool: `getStanding(courseId)` / `goalSeek(target, item)`.
- In chat the agent answers "what do I need on the final for an A?" grounded in the
  real rubric, and ties the answer to weak topics from Learning Progress
  ("you need 87; weakest topics: X, Y — want to drill?").

### Backend (FastAPI, Render — team-owned)
- New endpoints: courses CRUD, `POST /courses/{id}/syllabus` (upload+parse →
  proposed rubric), grade-item CRUD, `GET /courses/{id}/standing` (computed),
  keyed by studentId/auth. Reuse Auto Grader's PDF extraction.
- NOTE: backend lives in the team repo (`function` branch). Needs coordination
  with Jin / the backend owner — this is not a frontend-only feature.

## Approaches Considered
### Approach A: Course-context, agent-first (minimal UI) — not chosen
Smallest build; goal-seek lives only in chat, one modest panel for upload + rubric
+ grade entry. Rejected for now: user wants an always-visible standing surface.

### Approach B: Dedicated Grades tab — CHOSEN
Full gradebook surface + agent access. Always-visible standing, demo-friendly,
clear home. Cost: more UI; risk of "calculator with a login" if the chat loop is
treated as an afterthought (mitigated by making agent integration a v1 requirement).

### Approach C: Fold into Learning Progress (mastery + grades unified) — deferred
Topics carry both mastery and graded-item links; goal-seek ties weak topics to
grade weight. Strongest long-term, but biggest data-model lift and couples to the
sidebar refactor still mid-flight. This is the v2 trajectory B grows into.

## Open Questions
- Rubric edge cases: drop-lowest, extra credit, curves, "final replaces midterm if
  higher", attendance. v1 = weighted categories + letter cutoffs + drop-lowest;
  flag exotic rules as "edit manually." Confirm which rules to support in v1.
- How tightly do grade categories map to Learning-Progress topics in v1? Proposed:
  loose (agent suggests weak topics after the number); tight mapping = C/v2.
- Where exactly in the nav does "My Course" sit relative to Learning Mode?
- Auth requirement: does grade entry require sign-in (persistence), or allow local
  draft for signed-out? Proposed: sign-in required to save.

## Success Criteria
A student can: upload a syllabus, confirm the parsed rubric in under ~2 minutes,
enter their grades, and — while chatting in Learning Mode — ask "what do I need on
the final to get an A?" and get a **correct, rubric-grounded** number that also
points at their weak topics. The number matches a hand-calculation off the syllabus.

## Engineering Review: Locked Architecture (plan-eng-review, 2026-06-02)

**Scope decision:** Approach B, **phased**. Phase 1 = the wedge slice (full data model
+ syllabus parse + deterministic math + agent injection + a minimal standing surface).
Phase 2 = gradebook polish + exotic rubric rules. A is a strict subset of B; nothing in
phase 1 is thrown away.

**[EUREKA] The goal-seek engine is the moat, not the context.** RogerHub and
spreadsheets assume *static* per-item weights. Real rubrics use *conditional* weights
(lowest exam counts less, drop-lowest, best-N-of-M, replace-if-higher) that a
fixed-weight calculator structurally cannot compute. The math itself is defensible,
separate from "lives where you study." This moved conditional weighting from a deferred
edge case into phase-1 core.

### Data model (phase 1)
```
Course (Mongo, keyed by Firebase email)
├─ id, name, term, syllabusRef?
├─ rubric:
│    ├─ categories: [{ name, weight, rule }]      rule ∈ uniform | dropLowestK(k) | rankWeights([w1..wn])
│    └─ cutoffs:    [{ letter, min }]             e.g. A>=93, A->=90, ...
└─ items: [{ category, name, score, maxScore }]   ← EMBEDDED (no courseId, no N+1)
```

### Goal-seek solver (the moat): deterministic + piecewise
```
goal_seek(target_letter, unknown_item):
  needed_category_pts = cutoff(target) - (weighted sum of all OTHER categories, current)
  within the unknown's category, weights are assigned BY SCORE RANK:
        ┌─ assume unknown lands in rank slot r  → it takes weight w[r]
        │  the other items shift into the remaining slots
        └─ solve needed score for that slot; if the solved score would NOT actually
           land in rank slot r, move to the next slot (piecewise) and re-solve
  return min feasible score, or "infeasible" (>maxScore) / "already met" (<=0)

  worked example (your case): Exams = 25 pts, 4 exams, lowest→4 pts, others→7 pts.
  e1,e2,e3 known; e4 unknown. If e4 < min(e1,e2,e3): e4 weight = 4, and the prior
  min moves to a 7 slot. Else e4 weight = 7 and the current min stays at 4.
  → the needed score is piecewise; a fixed-weight calculator (RogerHub) cannot express it.
```

### Data flow
```
 syllabus.pdf ─► extract_pdf_text_safe (text layer, whole doc)
                   │  └─(scan, no text)─► vision-OCR shared helper (D3) ─► text
                   ▼
              rubric-extraction LLM call ─► proposed rubric {categories[rule], cutoffs[]}
                   ▼
              HUMAN CONFIRM / EDIT (always; weight-sum = non-blocking warning)   ← premise 3
                   ▼
              Course (Mongo, email-keyed, items embedded)
                   ▼
 grades entered ─► grades_math.compute_standing / goal_seek   (deterministic Python, ONE impl)
                   ├──────────────► GET /api/courses/{id}/standing ─► /grades standing card
                   └──────────────► inject into /api/chat system_content (grade-intent gated)
                                          ▼
                              agent: "need 87 on the Final; weakest: X,Y — drill?"
```

### NOT in scope (deferred, with rationale)
- **Function-calling agent tool** (`goalSeek`/`getStanding`): phase 2; v1 uses
  context-injection (D4). Reason: `/api/chat` is single-shot today; a tool loop is a real lift.
- **Rich gradebook editor + drop-lowest/curve UI**: phase 2 (scope A). Commodity UI; ship the wedge first.
- **Exotic rubric rules** (curves, cross-category replace-if-higher, attendance): "edit
  manually" in v1 (D2). rankWeights covers the common conditional cases.
- **AutoGrader auto-fill of GradeItems** from graded papers: v2 wedge (reuses `/api/autograder/grade`).
- **Approach C** (mastery + grades unified in Learning Progress): v2 trajectory; couples to the sidebar refactor.
- **Separate grade_items collection / cross-course analytics**: revisit in v2 (D11).
- **`api.ts` -> `apiBase.ts` consolidation + delete**: deferred TODO (T11) (D6).
- **Frontend component tests** for editor/gradebook/standing card: phase 2 (D8) - tests would target UI that phase 2 reworks.
- **Goal-seek-in-chat behavioral eval**: manual checklist in v1 (D9); the number is unit-tested.

### Failure modes
| Codepath | Realistic failure | Test | Error handling | User sees |
|----------|-------------------|------|----------------|-----------|
| Syllabus text extract | scanned PDF, no text layer | T4 | vision fallback -> manual entry (D7) | "couldn't read it, enter manually" (clear) |
| Rubric LLM | bad JSON / wrong weights | T4 + eval T10 | best-effort, weight-sum warning, always-confirm | editor opens pre-filled + warning (clear) |
| goal_seek | infeasible (need > max) | T2 | "not reachable" sentinel | "can't reach an A from here" (clear) |
| goal_seek piecewise | rank-boundary off-by-one | T2 (boundary case) | deterministic; covered | correct number (no silent error) |
| compute_standing | weights != 100 | T2 | warn/normalize, never crash | warning in editor (clear) |
| chat injection | no active / multiple courses | T6 | gate on grade-intent + active course | agent omits grades gracefully |
| courses write | unauthenticated | T5 | require email -> 401 | "sign in to save" (clear) |
| from_pdf refactor | helper extraction alters behavior | T3 REGRESSION (IRON RULE) | regression test guards | textbook upload unchanged |

**Critical gaps (no test AND no handling AND silent): none.** Every failure has a planned
test, error handling, and a clear user-facing message.
